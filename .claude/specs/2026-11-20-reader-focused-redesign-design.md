# Reader-Focused Redesign — Design Doc

**Status:** resolved in conversation — awaiting final sign-off on this document before moving to the implementation plan.
**Source:** `redesign.md` (repo root) + conversation on 2026-11-20
**Note on location:** the skill default for design docs is `docs/superpowers/specs/`, but `docs/` in this repo *is* the Docusaurus content root — anything placed there gets built and published as a site page. This doc lives in `.claude/specs/` instead, which Docusaurus never touches.

## Intent & Why

`redesign.md` asks for the site to get out of the reader's way: no white background, no permanent navigation chrome fighting for attention, one article on screen at a time, and a way to resolve an in-the-moment "what does that mean" question without leaving the page. The reference point is prajwalhaniya.in/post — a bare, single-column, year-grouped list of posts with nothing else on the page.

Confirmed in conversation:
- Applies to the **whole site** — blog and the docs tree (HLD, LLD, Fundamentals, Design Patterns, everything) — not just the blog.
- Cross-document links (Table of Contents anchors, HLD↔LLD companion links, etc.) are unaffected — only the *persistent* navigation chrome goes away, not in-content links.
- The highlight-to-explain feature is **same-page concordance only**: highlighting text searches the rest of *that page* for other mentions of it and shows them in a panel. No hand-written glossary, no AI/backend call.
- The light/dark toggle **stays**, and light mode gets its own new non-white "paper" palette (option 2 of the choices put to you) rather than today's pure white or a dark-only site.

## Goals

1. No white background anywhere, on either theme — dark is the primary/default look; light mode (still reachable via the toggle) uses a warm off-white "paper" tone instead of today's pure white (`#ffffff`).
2. Every article (blog post or doc page) renders as a single focused page: full-width content, no sidebar tree competing for attention.
3. Topic (and now Blog) selection stays a single dropdown (it already is — see Current State); reaching a *specific* article goes through that topic's/blog's own Contents-style index page, not a flat list in the dropdown itself (see the revised approach below).
4. Highlighting any text, on any page regardless of length, opens a right-side panel listing every other place on that same page that contains the same text, each a clickable jump-to-location link.
5. A single toggle (top of page) turns the highlight feature on/off, defaulting to off — off means the panel and highlighting interaction don't exist at all; this is the "distraction-free" mode.
6. Content grouped sensibly for how it's actually consumed: blog posts by year (matching the reference site), docs topics by their existing category structure (already in place, not chronological content).

## Non-Goals

- Rewriting or reorganizing the prose of any existing doc or post.
- Introducing a backend/server. The site stays 100% statically hosted; the highlight feature is pure client-side DOM/text work.
- A hand-written glossary (explicitly decided against — concordance only).
- Changing what pages exist or their URLs.

## Anti-Goals (would mean this failed even if it technically works)

- Docs become *harder* to get around than before — losing the one-click path from an HLD doc to its LLD companion, or between a doc's own sections.
- The highlight panel coming up empty on a short page reads as broken rather than as the expected "nothing else on this page says that."
- Any existing internal link breaks.

## Current State (relevant to this change)

- **Docusaurus 2.4.1**, classic preset, statically hosted (no server).
- A "Topics" **navbar dropdown already exists** (`src/components/TopicsNavbarItem/index.js`): 14 topics (Programming, DSA, HLD, LLD, Design Patterns, etc.), each pointing at that topic's generated Contents page. This is most of goal 3 already.
- `sidebars.js` defines **one hand-written sidebar per topic** (not one autogenerated tree for the whole docs/ folder), each `collapsed: false` with a `generated-index` link. This is what currently renders as the *persistent* sidebar once you're inside a topic — that's the piece this change removes.
- Already swizzled: `DocCategoryGeneratedIndexPage` (a topic's Contents page), `DocCard`/`DocCardList`, `DocItem/Layout`, `PaginatorNavLink`, `Root.js`.
- `Root.js` already mounts one global, client-only widget — `NotesWidget` (a floating per-page notes button, `BrowserOnly`-wrapped, state in `localStorage`, keyed by page path). This is the exact pattern the highlight feature should follow, not a new pattern.
- This session already rebuilt the typography (Roboto, dark-gray headings/body, no divider borders, modeled on sre.google/workbook) and both a light and dark theme exist via `[data-theme='dark']` in `src/css/custom.css`.

## Approaches Considered

### Removing the persistent sidebar
- **A — CSS-only:** hide `.theme-doc-sidebar-container`, expand `.theme-doc-markdown`/content column to fill the freed width.
- **B — Swizzle the doc page's layout component** to not render the sidebar column in the DOM at all.
- **Picked: A.** This is a presentation change, not a data change. CSS delivers "reader sees no sidebar, content takes the full width" with far less surface area to break and is trivial to revert if something looks wrong. The sidebar's data is still computed by Docusaurus either way; on a static site that cost is invisible.

### Picking an article within a topic (replacing the sidebar's job)
- **A — Make the existing Topics dropdown context-aware:** outside a topic, list the 14 topics (as today). Inside one, list *that topic's* articles instead, plus a way back out to the topic list.
- **B — A second dropdown**, only visible inside a topic, next to the existing Topics one.
- **C — No in-article picker at all** — rely on the topic's existing Contents page (already built, already handles nested subcategories as drill-down cards) as the "pick an article" screen; browser back returns there.
- **Revised pick: C** (changed from an earlier draft that picked A, before checking real numbers). DSA alone has 113 leaf docs across 8 subcategories, and Development/HLD/LLD/Database/Tech_Fundamentals/programming all nest too — 283 leaf docs sitewide. A dropdown listing 100+ flat entries isn't "one control" in any reader-friendly sense, and none of those subcategories are flagged `collapsed: false`, meaning the *existing* sidebar already presents them as a drill-down, not a flat list — so a flat dropdown would be a regression in exactly the cases it matters most. Removing the sidebar doesn't actually hurt multi-level browsing here, because the Contents page's card drill-down is a separate, already-working path that was never part of the sidebar. The Topics dropdown's job stays exactly what it does today (jump to a topic's or now Blog's top-level index); getting to a *specific* article inside a topic goes through that topic's Contents page, the same as reaching a specific blog post goes through the year-grouped index (see below).

### Reaching the blog
The navbar today has only the Topics dropdown — the blog nav link is commented out in `docusaurus.config.js`, so `/blog` currently has no entry point at all. Fix: add **Blog as a 15th entry in the same Topics dropdown**, pointing at a year-grouped index page (the thing modeled on prajwalhaniya.in/post — year headings, flat list of post titles+dates underneath). From there, clicking a post is the same "Contents page → single article, no sidebar" path docs topics use. This keeps "one control picks where to go" literally true site-wide instead of leaving blog as a separate, undiscoverable island.

### The highlight-to-explain feature
Decided in conversation (same-page concordance). Implementation: a global, client-only React component mounted in `Root.js` next to `NotesWidget`, following its exact pattern (BrowserOnly, localStorage for the on/off toggle):
1. Listens for a text selection inside the article content.
2. On selection, scans that page's own rendered text for other paragraphs/headings containing the same text.
3. Opens a right-side panel listing each match as a jump-to-location link.
4. A toggle button near the existing light/dark switch turns the whole feature (selection listening + panel) on or off; state persists in `localStorage` the same way notes already do. **Defaults to off.** If it defaulted on, selecting any text for an ordinary reason — like copying a code snippet — would pop the panel every time, which is the opposite of "distraction-free." A reader who wants it opts in once, and the choice persists.

## Decisions Made in Conversation

- Scope: the whole site, not just the blog.
- In-content/cross-document links are unaffected by chrome changes.
- Highlight source: same-page concordance only, every page, any size — no glossary, no AI/backend.
- Dark is the primary/default look; the light/dark toggle stays, and light mode gets a new non-white palette rather than keeping today's pure white or going dark-only.

## My Calls (stated so they can be corrected)

- **Year-vs-category grouping:** "year" grouping applies to the **blog** (matches the reference site, and blog posts are inherently dated). Docs topics (HLD, LLD, Fundamentals, Design Patterns, ...) keep their **existing category grouping** instead of being forced into years — that content isn't chronological, and the category structure already works and is what the Topics dropdown already uses. If this is wrong and you want docs grouped by year too (e.g., by when each doc was added), say so.
- **Light palette (concrete proposal):** a warm off-white "paper" tone — around `#f7f4ed`/`#faf8f2` for the background rather than `#ffffff` — paired with the same dark-gray ink (`#424242`/`#515154`) and Roboto typography already built this session for dark mode. This fits the site's own "Tech Notebook" branding (the existing `NotesWidget`/"notebookIndex" naming already leans on a paper/notebook metaphor) better than either stark white or a second gray-on-dark scheme. Exact hex values are a builder-time detail, not something that needs another round of approval.
- **Toggle placement:** the highlight on/off switch sits next to the light/dark toggle in the navbar, so all "how this page looks/behaves" controls live in one place.
- **Highlight toggle default:** off (see "The highlight-to-explain feature" above for why).
- **In-topic/in-blog navigation:** goes through each topic's/blog's existing Contents-style index page (card drill-down), not a dropdown enumerating every article — see the revised pick under "Picking an article within a topic."

## What's Left to the Builder

- Exact concordance matching rules: case-insensitive vs. exact, minimum selected-text length before it searches, how multi-word phrases are matched, how the panel orders multiple matches on a long page.
- Panel layout/animation details (slide-in from the right, width, mobile behavior at narrow viewports).
- Whether the blog's year-grouping reuses Docusaurus's built-in blog-archive feature or needs a small custom index component (default: use what Docusaurus already provides unless it doesn't fit).
- Whether removing the sidebar changes the content max-width/measure (likely yes — content can use more of the freed width, within the same readability limits already established this session).
- Visual styling of the Contents/drill-down pages for topics with deep subcategories (DSA's 113 docs across 8 subfolders, etc.) now that they're the primary way to reach an individual article, not just a landing page.
